# ADR-094 — удобное добавление beta-узлов: инвентарь и предпроверка хоста

Статус: этап 1 реализован 2026-11-09. Этап 2 реализован в коде в тот же день по прямому поручению владельца (до этого он отложил его до конца пилота, затем попросил доделать); на реальном хосте до активации не доведён: кандидат `detourvpn-beta-germany` (Ubuntu 22.04) не прошёл установку, нужна Ubuntu 24.04. Этап 3 не сделан.
Продолжает ADR-092 (несколько узлов в одном клиенте), ADR-061/062 (staged provisioning и
активация), ADR-052 (сетевой путь узла).

## Контекст

Владелец хочет добавлять новые серверы в список без ручной сборки команд, и потом добавлять ещё.
Сервер и клиент уже умеют несколько узлов (до 16): строки `vpn_nodes`, манифест окон v3, каталог
`GET /api/v1/nodes`. Но цепочка, которая готовит и включает узел, жёстко привязана к одному узлу:

- `bind_beta_node_config.py`: зашиты адреса API и узла, ключ провижининга и манифест ровно из
  одного узла;
- `activate_beta_node.py`, `check_beta_node_status.ps1`: fail-closed проверка имени
  `detourvpn-beta-helsinki`;
- `provision_beta_node.py` уже принимает `--name/--region/--country-code/--city`.

Это сделано намеренно (ADR-092: параметризовать fail-closed проверку, пока нет конкретного
второго узла). Эти скрипты содержат более 1 500 строк оператор-кода со встроенными удалёнными
программами, и менять их без реального второго хоста нельзя честно проверить.

## Решение

Идти по этапам, каждый этап проверяем отдельно. Узел нельзя считать добавленным по этапу 1.

**Этап 1 (сделан): один источник правды и безопасная проверка кандидата.**

- `infra/beta/nodes.json` описывает узлы: имя, регион, страна, город, адрес, SSH-пользователь,
  имя ключа (только `~/.ssh/detourvpn-*`), SSH-порт, диапазон UDP-портов слотов (не более 16).
  Реальный файл содержит адреса и лежит в `.gitignore`; коммитится только
  `nodes.example.json` с адресами документации. `scripts/beta_nodes.py` читает файл строго:
  неизвестные и пропущенные поля, дубликаты имени, региона и адреса, IPv6, не публичные адреса,
  больше 16 узлов, файл-ссылка и файл больше 64 КиБ отклоняются фиксированными кодами без
  значений.
- `scripts/check_candidate_node.py --node <имя>` подключается по SSH (`BatchMode`,
  `StrictHostKeyChecking=yes`, один ключ, без shell и без записи на хост), выполняет одну
  фиксированную программу только на чтение и печатает вердикт: имя проверки и пройдена ли она.
  Адреса, имена хостов и сырой вывод не печатаются и не сохраняются. Обязательные проверки
  повторяют ADR-052: root, поддерживаемая ОС (только Ubuntu 24.04, см. поправку ниже), x86_64, systemd и `systemd-executor`,
  ровно один маршрут по умолчанию, публичный IPv4 назначен интерфейсу напрямую, `ip_forward`
  уже включён, UDP-порты слотов свободны. Память и диск только предупреждение, пороги те же, что у
  staging-оператора, и не являются универсальными.
- Вердикт `ready` означает только выполнимые предусловия. Это не доказательство handshake,
  source-bound egress, атрибуции трафика и не разрешение включать узел (ADR-061/062).

**Этап 2 (реализован 2026-11-09, см. ниже).** Исходная формулировка: Подставить в `bind`, `activate` и
`status` данные узла из инвентаря вместо констант (флаг `--node`, по умолчанию Helsinki), оставив
fail-closed сверку имени и региона. Манифест окон должен собираться из всех активных узлов с
сохранением секретов уже настроенных; отдельный ключ провижининга на узел. Проверка только на
реальном втором хосте по ADR-061/062: handshake, egress, учёт.

**Этап 3.** Одна команда «включить, выключить, поправить страну» для готовых узлов (аналог
разового `set_beta_node_country.py`) и, при необходимости, экран в админке.

## Безопасность и ограничения

- SSH-доступ к новому хосту нужно подготовить вручную: добавить ключ `detourvpn-*` и сверить
  отпечаток хоста по консоли провайдера до первого подключения. Принятие нового ключа хоста
  автоматически не поддерживается.
- Инвентарь не хранит секреты (ни ключей, ни паролей, ни токенов), только имя файла ключа.
- Проверка не меняет ни хост, ни БД, ни API. Выход 0 только при `ready`, 1 при `not_ready`, 2 при
  ошибке инвентаря или SSH.
- Внешние панели (3x-ui, Remnawave, Xray/Reality) сюда не входят: это отдельный класс узлов и
  отдельный ADR (адаптер, учёт трафика, хранение доступов панелей).

## Проверка

38 тестов в `services/api/tests/test_beta_nodes.py`: валидация инвентаря, чистая функция оценки
(каждый сбой попадает ровно в свою проверку, нехватка данных закрывает), разбор вывода,
CLI с подменой SSH (нет адреса в выводе, чек-файл не перезаписывается, фиксированные коды ошибок,
в команде после `bash` нет метасимволов оболочки). Предпроверка прогнана на действующем beta-узле,
только чтение: `verdict=ready`, все 11 проверок зелёные.

## Поправка 2026-11-09 и этап 2 (реализация)

**Поддерживаемая ОС узла: только Ubuntu 24.04.** Первая версия предпроверки разрешала Ubuntu
22.04 и Debian 12, это была ошибка. `beta_slot_bootstrap.py` узнаёт переходный процесс запуска
`ip netns exec` только по `systemd-executor` из systemd 255. На Ubuntu 22.04 (systemd 249)
установка на кандидате `detourvpn-beta-germany` честно упала на запуске bootstrap с
`slot_core_identity_conflict`; откат прошёл, на сервере не осталось файлов, юнитов и сетевых
объектов узла. Теперь предпроверка требует `ubuntu 24.04` и `/usr/lib/systemd/systemd-executor`.
Расширять bootstrap на старые systemd без отдельной проверки не стали. Старый receipt
`beta-node-germany-preflight-20261109.json` (вердикт `ready` на 22.04) устарел; актуальный:
`beta-node-germany-preflight-20261109-corrected.json` (`not_ready`).
Также в инвентаре были неверные UDP-порты слотов: слоты используют 51900 + номер (51901–51916),
а не 51820–51829.

**Установка узла** (`scripts/install_beta_node.py`, по умолчанию сухой прогон): предпроверка
кандидата, сборка пинованного пакета (`package_beta_node`), свежие ключи слота в памяти (на диск
ПК не пишутся), загрузка по SSH и одна фиксированная программа на новом хосте: uv 0.11.17 и
CPython 3.13.12 с пинами SHA-256, снятыми с рабочего узла, venv с теми же пятью пакетами по
хешам, три проверенных systemd-юнита, закрытый слот. Агент не запускается. Любая ошибка откатывает
только созданное этим запуском; при падении bootstrap печатаются только фиксированные коды.

**Подключение к control plane** (`scripts/connect_beta_node.py`, сухой прогон по умолчанию):

- `register` создаёт строку узла `disabled`; ключ идемпотентности детерминирован по имени узла;
  при необходимости заменяет помощник `provision_beta_node.py` на хосте (только с известного
  хеша, с копией и откатом);
- `bind` кладёт `agent.json` и credential на узел, добавляет IP узла в `remote_ip` Caddy (одна
  строка, `caddy validate`, `reload`, проба Mini App, откат) и вносит узел в манифест окон (копия,
  атомарная замена). API читает манифест на каждый запрос, поэтому перезапуск API не нужен и
  работающий узел Хельсинки не перезапускается;
- `activate` переводит строку в `active`, запускает агент, ждёт аутентифицированный poll и
  включает автозапуск агента; при сбое останавливает агент и возвращает `disabled`;
- `rollback` и `status`.

Для Хельсинки команды отказывают (`connect_existing_node_refused`).

**Что это не доказывает.** Ни один шаг не доказывает доступность UDP-порта слота у провайдера,
handshake, source-bound egress или атрибуцию трафика: их нужно проверить физическим подключением
по ADR-061/062 до приглашения кого-либо на этот узел.

**Наблюдение по Хельсинки (только чтение, не исправлено).** `detourvpn-beta-node-agent.service`
активен, но не был включён в автозапуск; владелец включил его (`systemctl enable`, 2026-11-09).

**Проверка.** `test_beta_nodes.py`, `test_install_beta_node.py`, `test_connect_beta_node.py`:
126 тестов. Удалённые программы `connect_beta_node.py` прогнаны в режиме только чтения на реальном
API-хосте (`status`, `register` без `--execute`): настройки, манифест из одного узла и Caddy
проходят проверки; правка Caddy на реальном файле меняет ровно одну строку и идемпотентна.
Установка на реальном хосте дошла до запуска bootstrap (uv, Python, venv, пакеты, файлы, юниты
прошли), дальше см. поправку выше.
