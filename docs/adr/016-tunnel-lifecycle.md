# ADR-016: выдача конфигурации и отзыв туннеля

Status: **Proposed — I-012 contract preparation only**, 2026-10-18.

## Контекст

I-006 хранит публичный ключ устройства и отзывает связанные с ним сессии.
I-009 аутентифицирует узел только для получения usage samples. I-010/011 пока
не подтвердили установку узла, Android handshake или реальный egress IP.
Поэтому сейчас нельзя считать запись в PostgreSQL установленным peer или
утверждать, что `DELETE` немедленно прекратил трафик.

## Предлагаемый контракт

`POST /api/v1/tunnels` принимает UUID idempotency key и идентификатор **своего**
активного устройства. Успех разрешён только с действующей сессией, привязанной
к этому устройству, пригодным узлом и положительной проверкой всех условий
выдачи. Ответ содержит только конфигурацию для устройства, без private device
key и без серверных секретов. Клиент создаёт private key локально; контрольная
плоскость хранит только public key и минимальную служебную конфигурацию. Повтор
с тем же key и теми же параметрами не создаёт второго peer; тот же key с другими
параметрами возвращает стабильный conflict. Чужой и неизвестный device/tunnel ID
не раскрываются различимыми ошибками.

Нельзя отправлять клиенту конфигурацию как готовую к подключению, пока узел не
подтвердил применение конкретного peer и сервер не проверил, что подтверждение
пришло от назначенного узла. Запись намерения в БД имеет отдельный статус
`provision_pending`. `active` означает подтверждённое состояние узла, но сам по
себе этот статус не доказывает handshake или маршрут: это доказывается I-011.
Если подтверждения нет, API возвращает статус ожидания/ошибку без фиктивного
`connected`. Точные поля конфигурации, expiry и endpoint будут выбраны после
I-011 source/build/network evidence, а не по догадке из WireGuard reference.

`DELETE /api/v1/tunnels/{id}` атомарно сохраняет намерение отзыва и команду
узлу. До подтверждения удаления peer состояние `revoke_pending`; API не
сообщает `revoked`. Если узел недоступен, запрос остаётся видимым оператору и
повторяется идемпотентно. Повторный DELETE не создаёт новую команду. Отзыв
устройства из I-006 должен в той же транзакции пометить все его туннели к отзыву
и сохранить команды. Простое закрытие login session не заменяет node revoke.

## Узловой протокол и согласованность

Текущий agent v1 принимает только usage samples; I-012 требует отдельной
versioned capability для узких операций `add_peer`, `remove_peer` и
подтверждения фактически применённой версии конфигурации. Никаких произвольных
shell-команд, путей файлов, URL, DNS-запросов или payload traffic в агентском
контракте. Узел идентифицируется своим credential и TLS ingress; node ID из
тела команды не используется как авторизация. Команда имеет собственный UUID,
порядковую версию peer и идемпотентный результат. Подтверждение с устаревшей
версией не должно оживлять отозванный peer.

Пользовательская запись, outbox-команда, назначение узла и idempotency receipt
должны фиксироваться одной транзакцией. Применение на узле — отдельный шаг;
PostgreSQL commit нельзя трактовать как успех data plane. После восстановления
связи оператор/агент сверяет desired и observed peer sets. Счётчики позднего
трафика продолжают учитываться по I-008, даже если устройство уже отозвано.
Откат миграции с непустыми tunnel/outbox records должен отказываться без потери
данных. Порядок блокировок и гонки create/delete/device revoke/node ack должны
быть определены и проверены на PostgreSQL до реализации.

## Неопределённые решения, блокирующие выдачу

1. **Владение ключом.** Регистрация канонического public key в I-006 не
   доказывает владение private key. Нужен проверенный native handshake или
   другой безопасный proof; X25519 public key не используется как подпись.
2. **Ограничение перерасхода.** I-008 ведёт учёт, но не останавливает узел.
   Срок/объём lease, reservation, поведение при недоступности API и измеримый
   предел перерасхода не утверждены. До этого не выдавать рабочую конфигурацию
   пользователю и не заявлять quota hard cutoff.
3. **Сетевые параметры.** Node endpoint, peer address, IPv6/DNS policy, MTU,
   server public key, AWG параметры и renewal должны подтверждаться выбранным
   I-011 движком и staging сетью. Не вставлять dev values в production config.
4. **Секреты и эксплуатация.** Node private key создаётся на стенде; доставка
   device config, retention, redaction, node credential rotation и HTTPS ingress
   должны быть проверены до удалённого теста. В логах нет browsing metadata,
   private keys и полного tunnel config.

До закрытия этих пунктов I-012 может иметь только внутренние контракты и
локальные synthetic проверки. Публичный рабочий tunnel API и DoD `Revocation
tests` требуют узлового применения и реального прекращения доступа на стенде.

## Альтернативы и последствия

- Сразу отвечать `204` после записи в БД — отклонено: узел может продолжать
  пропускать трафик, а пользователь увидит ложное подтверждение.
- Бессрочный peer с попыткой удаления при доступности узла — отклонён: при
  разрыве связи нет ограниченного времени доступа.
- Хранить device private key на backend — отклонено: противоречит модели
  локальных ключей и расширяет поверхность утечки.
