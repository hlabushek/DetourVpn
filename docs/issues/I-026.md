# I-026 — secure Telegram-to-Android OTP entry

Status: **accepted for the owner-only live flow on 2026-10-26: Telegram Mini App → OTP → Android sign-in, account device binding, `initData` replay rejection, and duplicate OTP rejection observed. No friend onboarding or VPN data-plane acceptance is implied.**

Актуальный срез на 2026-10-26: владелец открыл beta bot Mini App в Telegram на
Android, запросил код и подтвердил вход в Android client; кабинет показал
авторизованное состояние. API изменения с квитанцией развернуты на отдельном
beta API host, DB revision `0017_login_delivery_receipt`, readiness/health=200.
После выкладки read-only агрегатный запрос обнаружил одну запись `api_accepted`
за 15 минут, совпадающих по времени с повторным входом владельца. За 30 минут
видны один OTP issue, одна использованная попытка, одна native-сессия с
`device_id` и отсутствие нового device-key row; это согласуется с успешным
повторным входом с уже зарегистрированного телефона. Bot API `ok=true` не
подтверждает прочтение сообщения, а агрегаты без ID не связывают строки
однозначно друг с другом. При повторном открытии того же Mini App владелец
получил точное сообщение `Этот вход уже использован. Откройте Mini App заново.`;
агрегаты активных replay digest и Mini App-сессий при обновлении остались 2/2.
Текст UI соответствует backend-коду `init_data_replayed` (HTTP 409), но raw
HTTP receipt и `initData` не собирались. Hosted повтор OTP позднее проверен
отдельным debug probe. Read-only query связал единственную consumed попытку,
единственную native-сессию и их точные timestamp; также подтверждена одна
активная запись устройства у аккаунта. Сырой ID попытки, аккаунта или устройства
не выводился.
См. `../evidence/i-026-beta-live-delivery-receipt-20261026.json`.
Датированные ниже pre-activation заметки сохраняют историю и не заменяют более

## Цель и граница

Дать участнику разрешённой бесплатной закрытой беты пройти Android `/auth/start`
→ Telegram `/start <request_id>` → проверенный Mini App `initData` → одноразовый
код → Android `/auth/verify`, сохранив FastAPI/PostgreSQL единственным владельцем
identity, OTP и сессий. Telegram Serverless показывает приглашение в Mini App,
но не получает права выдавать коды или создавать VPN-сессии.

Исходники подтверждают, что backend уже реализует `/api/v1/auth/start`,
`/api/v1/auth/verify`, защищённый `/api/v1/telegram/webhook` и HMAC-проверку
Mini App `initData`. Локальная реализация добавляет выдачу Android OTP после
Mini App identity check. Hosted menu deployment не подтверждает запуск кнопки
в Telegram, доставку кода или Android login; см. `../verification-telegram-bot.md`,
ADR-032 и ADR-043.

## Зависимости и предварительные ворота

1. Проверить штатный runtime secret injection, прежде чем проектировать relay.
   Не угадывать `process.env`/API и не класть секрет в исходники, SQLite,
   module config или ответы пользователю.
   2026-10-25: в BotFather account overview не обнаружен отдельный раздел
   Secrets; проверка runtime globals/context/SDK exports в `tgcloud run` и
   endpoint Console вернула false для всех известных env/secret интерфейсов.
   Endpoint `runtimeProbe` сохранён в account и синхронизирован в локальный
   проект. Повторная проверка BotFather UI показала только CLI Access, Handlers,
   Endpoints, Library, Database и Mini App Files; отдельного Secrets раздела не
   было. Это не проверяет скрытую/непривязанную настройку или подстановку
   disposable secret. Полный результат: `../evidence/i-026-serverless-runtime-probe.json`.
   Уточнение по официальной документации и закреплённому CLI: endpoint вызывается
   из Mini App с проверенным `initData`; CLI Access token авторизует операции
   самого CLI и локально сохраняется в `.tgcloud/credentials`. Ни одно из этого
   не является подтверждённым способом аутентифицировать доставку `/start`
   Updates к FastAPI. CLI Access token не является подтверждённым runtime
   secret. При просмотре UI его значение попало в accessibility output; оно не
   копировалось и не использовалось. Владелец отложил ротацию; этот credential
   не использовать и не открывать повторно. Перед будущими cloud CLI операциями
   вопрос ротации нужно решить отдельно. Вместо relay выбран
   Mini App flow, где FastAPI самостоятельно проверяет HMAC `initData`; решение
   и контракт зафиксированы в ADR-043.
2. Передавать в Mini App только случайный 32-hex `request_id` через URL fragment;
   не включать в URL `initData`, OTP, verifier или session token.
3. Endpoint `/api/v1/auth/mini-app/request-code` должен проверять подпись и
   свежесть `initData`, одноразовый replay, состояние и subject binding попытки,
   OTP rate limits, а код отправлять только через backend `TelegramSender`.
   Mini App не получает Android session или tunnel permission.
4. Не менять webhook существующего бота до отдельного разрешённого live окна,
   проверки исходной конфигурации/rollback и подтверждения, что новый маршрут
   принимает сообщения. Секреты вводятся владельцем только локально в
   доверенном интерфейсе/терминале, никогда в чат или evidence.

## Приёмка I-026

- Local deterministic tests: валидная подпись Mini App → OTP → Android verify;
  неправильная/просроченная подпись, replay, неверный UUID, чужой/expired/
  consumed challenge, rate limit и неоднозначная доставка fail closed; код и
  `initData` отсутствуют в URL fragment, API response, logs/errors.
- Проверки replay/rate/concurrency используют disposable real PostgreSQL.
  Telegram sender doubles и подписи `initData` явно synthetic TEST ONLY.
- Hosted acceptance в отдельно согласованной среде: настоящее сообщение
  `/start` в собственном test chat, Mini App открывается с attempt fragment,
  настоящий Telegram `initData` проходит backend, код доставлен в тот же private
  chat, Android verify и device pairing успешны; повторный `initData` и OTP
  отклоняются. Сервер сохраняет только ограниченный статус Bot API (`pending`,
  `api_accepted`, `unknown`) и время; `api_accepted` не означает, что человек
  увидел сообщение. Секреты, код, raw `initData` и личный Update не сохраняются.
- Обновить `docs/verification-telegram-bot.md`, runbook и ADR фактическими
  результатами; live login объявлять принятым только после hosted и Android
  acceptance, а не по локальным тестам или deployment receipt.

## Ворота бесплатного закрытого теста и отдельные требования

Для приглашения друзей необходимы: рабочий настоящий OTP login; постоянная,
изолированная beta control plane/API/DB и VPN node с доступом по приглашениям,
ограниченными ресурсами, отзывом доступа и проверенным backup/restore;
пройденные Android data-plane/privacy acceptance для поддерживаемого сценария;
понятная инструкция, поддержка и согласие на минимальную диагностику. Бесплатная
закрытая группа не требует платежей, платёжного sandbox, тарифного каталога,
рекламных/реферальных кампаний или публичной регистрации.

Перепроверка локального I-026 состояния 2026-10-25: API/PostgreSQL **13 passed**;
Mini App **8 passed** и TypeScript/Vite build passed; Serverless bot **45 passed**,
runtime boundary check passed для 8 модулей. Это подтверждает только локальные
контракты с synthetic TEST ONLY Telegram `initData`/sender. HTTPS beta origin и
`miniAppUrl` остаются пустыми, поэтому live OTP login не принят.

Локальная подготовка 2026-10-26: по ADR-055 конфигурация бота допускает
canonical public IPv4 HTTPS URL только для `miniAppUrl`, чтобы закрытая beta могла
обойтись без домена при условии работающего IP TLS. Приватные/зарезервированные,
неканонические IPv4, порты, query и fragment запрещены; прочие внешние ссылки

Публичный/платный запуск дополнительно требует legal/payment gate, security
