# Готовый текст следующей issue

**Title:** I-002 — Утвердить идентичность и выбрать лицензируемую Android tunnel integration

**Priority:** P0  
**Depends on:** I-001; исходные TECHNICAL_SPEC/ROADMAP и ADR-001/002/003.
**State:** Research delivered 2026-10-18; acceptance blocked (B1–B6).
На GitHub issue не создана. Владелец выбрал основной вход кодом из Telegram-бота;
технический контракт ADR-001 и решения по SDK ещё не приняты окончательно.

## Проблема

До авторизации и нативного VPN нельзя безопасно выбирать библиотеку, recovery flow
или совместимые версии только по общей документации. Текущие ADR — Proposed.

## Объём

1. Прочитать architecture-review, разобрать R02–R05/R11 и уточнить решения владельца.
2. ADR-001: зафиксировать основной метод входа, допустимый fallback/recovery/linking,
   session/revocation модель, admin MFA boundary, персональные данные и зависимости.
3. ADR-002/003: сравнить минимум AWG-кандидат и reference вариант; записать точные
   upstream URL, immutable commit/artefact/checksum, Android API/ABI, server/client
   protocol/config versions и план воспроизводимой сборки.
4. Создать `docs/licensing-checklist.md`: компонент/revision/SPDX, native/transitive
   deps, linking/redistribution, NOTICE/исходники, источник доказательства,
   результат/ответственный. Root license без bundled deps недостаточна.
5. Создать `docs/compatibility-matrix.md`: что подтверждено source/build evidence,
   что требует I-011 на физическом телефоне; неподтверждённые ячейки не помечать pass.
6. Зафиксировать go/no-go и blockers. ADR перевести в Accepted только после явного
   решения владельца и достаточных доказательств; при blockers оставить Proposed
   с точной причиной и необходимым следующим действием.

## Критерии приёмки

- [x] Владелец выбрал код из Telegram-бота; ADR-001 обновлён. Описаны pairing,
      защита от takeover/duplicate quota и отсутствие пока независимого recovery.
      B4 теперь касается технического контракта/retention, а не повторного выбора способа.
- [x] Есть threat model сессий/recovery; секретов и реальных provider credentials нет.
- [x] У кандидатных SDK/движка указаны точные revisions и source evidence, а не «latest».
- [x] Licensing checklist перечисляет native/transitive компоненты; выбор модели
      распространения владельцем — «пока не решено», clearance B2 открыт.
- [x] Матрица отделяет source evidence от BUILD/DEVICE NOT RUN.
- [x] По каждому ADR есть решение владельца либо явно документированный blocker;
      общий go возможен только при Accepted ADR и закрытых блокирующих рисках.
- [x] `uv lock --check`, Ruff format/lint, mypy, pytest, OpenAPI check проходят,
      опубликован отчёт изменений и неподтверждённых предположений.

Research deliverables: `docs/licensing-checklist.md`, `docs/compatibility-matrix.md`,

Это не пометка всех ADR Accepted или разрешение на выпуск tunnel binary.

## Вне объёма

Production/staging deploy, VPS/аккаунты/платежи, Telegram/SMTP интеграция,
новый auth API/DB schema, полный Flutter UI и реальное проксирование трафика.
Физический tunnel spike остаётся I-011. Существующий I-003 нужно перепланировать
из-за уже выполненного health в стартовом промпте; другие issues не реализуются.

**Результат:** документация, конкретный допустимый SDK/engine plan и решение
go/no-go. При недостатке evidence «всё утверждено» не является допустимым результатом.
