# I-031 — ручной выбор beta VPN-локации на существующих узлах

**Статус:** локальная заготовка. Реальные дополнительные хосты не проверены и не включены.

## Цель

Дать участникам закрытой beta возможность выбрать вручную одну из проверенных
VPN-локаций. API/control-plane узел в Helsinki остаётся только управляющим
сервером и никогда не появляется в каталоге VPN. Владелец сообщает о четырёх
отдельных VPN data nodes в нескольких локациях; их фактические роли, владельцы,
провайдеры и текущее состояние ещё требуется свести с инвентарём. Не публиковать
их IP-адреса, ключи и учётные данные в issue или клиентской диагностике.

Начальный owner-reported inventory, ещё не сверенный с host identities:

| Роль/локация | Текущее подтверждение |
|---|---|
| Helsinki — control plane/API | Владелец распознаёт его как управляющий сервер; не VPN-локация |
| Helsinki — VPN data node | Показывался в beta catalog как `available`; физический handshake не подтверждён |
| Frankfurt — VPN candidate | Сообщён владельцем; host identity и состояние неизвестны |
| Dronten — VPN candidate | Сообщён владельцем; host identity и состояние неизвестны |
| Germany, city/provider TBD — VPN candidate | Сообщён владельцем; провайдер предположительный, host identity и состояние неизвестны |

Это таблица для последующей сверки, а не обнаруженный или разрешённый список
хостов. В существующем checkout нет подтверждённых Frankfurt/Dronten target
identities или Hetzner mapping.

## Уже реализовано

- Android `WindowConnectionController` запрашивает каталог API и показывает
  каждую сконфигурированную ноду с её городом/регионом и причиной доступности.
- Экран позволяет выбрать конкретную доступную ноду. Он не подменяет явный выбор
  другим сервером при ошибке.
- API формирует каталог из операторского root-owned `WindowManifest`, а не из
  произвольных записей пользователя. Контракт допускает до 16 нод и до 16
  изолированных slots на ноду.
- В `WindowSlot` endpoint, server public key и header protection key связаны с
  конкретным slot; дубликаты node IDs, endpoints и public keys запрещены.
- Owner Pixel увидел beta Helsinki node со статусом `available`. Последняя
  bounded попытка не подтвердила handshake, поэтому эта нода ещё не принята как
  рабочая VPN-локация и список для тестеров пока не готов.

Новые библиотеки и переписывание списка локаций не нужны. Текущий UI/API
составляют необходимый multi-location skeleton.

## Этапы

1. **Свести инвентарь, только чтение.** Сопоставить каждый сервер с ролью
   control-plane или data-plane; проверить владельца и разрешённую среду,
   провайдера/ASN, регион, ОС/kernel, engine revision, публичный endpoint, срок
   аренды, адресацию, маршрутизацию, forwarding, firewall/provider security-group,
   текущие unit/process и старые runtime credentials. Историческое использование
   не доказывает текущую готовность.
2. **Выбрать beta targets.** Не включать control-plane в каталог. Не смешивать
   старый staging, development и production. Если роль или host identity
   не подтверждается — остановить этот target и запросить у владельца уточнение.
3. **Подготовить каждый data node отдельно.** Совместимые pinned binaries и
   capabilities; отдельные стабильные slots, node identity и credentials; точный
   город/страна в операторском каталоге; root-only файлы вне checkout; private
   configs и credentials никогда не попадают в Git, receipts или чат.
4. **Проверить реальную сеть каждой локации.** Проверить control-plane polling,
   внешний UDP ingress и handshake, ограниченный тестовый egress/usage,
   disconnect/revoke/cleanup и повторный выбор. Свежий agent heartbeat сам по
   себе не означает рабочий туннель. Не добавлять локацию в доступный каталог до
   прохождения её отдельной физической acceptance.
5. **Показать локацию честно.** Каталог содержит только проверенные ноды; город и
   страна понятны пользователю; недоступная, stale, занятая или неподтверждённая
   нода не рекламируется как рабочая. Ручной выбор не является failover.

## Границы и критерии приёмки

- Начать с одной дополнительной одобренной ноды; затем добавлять по одной.
- В закрытый catalog попадают только проверенные beta data nodes.
- У каждой ноды уникальные node/slot identity и отдельные секреты.
- Проверки подтверждают, что disabled/stale/full nodes нельзя подключить и
  клиент не переключается на другой регион молча.
- Физический тест каждого региона проходит signed Android beta APK и фиксирует
  handshake, ограниченный egress, измеренный usage, disconnect и server-side
  cleanup без содержимого трафика, URL или DNS-истории.
- Смена региона не меняет баланс и не создаёт второе устройство; автоматический
  failover, выбор по latency, покупки/перенос серверов и новые DNS/account
  операции в issue не входят.
- До завершения проверки конкретной локации не выдавать её тестерам как доступную.

## Безопасность и ограничения

Текущая implementation рассчитана на прямой публичный IPv4 endpoint и один
выбранный uplink; provider NAT, multihoming и асимметричная маршрутизация не
поддерживаются. Для каждого нового host надо подтвердить его сетевую политику,
kernel forwarding и UDP path отдельно. Не переносить старые секреты из прошлых
staging-роллаутов и не менять существующие beta/API targets при инвентаризации.

Hosted provisioning, изменения firewall/provider console и API manifest требуют
отдельного согласования target и конкретного действия. До этого issue является
локальным планом; активный invite и текущие узлы не меняются.
